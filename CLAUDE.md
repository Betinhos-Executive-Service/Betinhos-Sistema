# CLAUDE.md — Sistema Betinhos

## Publicação (develop → DEV, main → PROD)

Decisão do Renan, 05/11/2026: o GitHub é o único caminho de publicação. Ninguém publica pelo Power Platform; as soluções continuam fazendo o transporte por baixo.

- **Branches.** PRs entram na `develop`. A `main` só recebe a `develop` inteira (PR `develop → main`, merge do Renan). O ruleset "main só da develop" exige PR e o check `origem-main` (`origem-main.yml`); a `develop` é a branch padrão do repositório. O merge automático do plantão (`.claude/entrega-autonoma.json`) vai só até a `develop`, nunca na `main`.
- **DEV.** Push na `develop` dispara o workflow "Deploy" (`deploy.yml`, environment `dev`, conta de serviço), que publica a tela (`pnpm push`) e os plugins (`packages/deploy/push-plugins-dev.ps1`) que o DEV ainda não tem e distribui uma vez no fim. `packages/deploy/pendentes-dev.ps1` decide comparando o HEAD com o commit que o DEV registra: descrição do `cr40f_SistemaBetinhos.html` (`vX.Y.Z <sha>`) e de cada assembly `Cr40f.<Nome>.Plugin` (`<sha>`, gravado pelo registrador só no CI). A versão da tela parte da maior entre a do repo e a publicada, então nunca retrocede. Testes dos plugins rodam no PR (job `plugins` do `ci.yml`, só os tocados); o Deploy não repete. As chaves de assinatura vêm dos secrets `PLUGIN_SNK_<NOME>` do environment `dev` e a configuração do plugin de acesso das variáveis `ACESSO_*`. Publicação local de plugin grava descrição vazia e a trava do PROD recusa até o Deploy publicar de novo (`workflow_dispatch` com `forcar_plugins`). **Flows existentes publicam sozinhos** no mesmo Deploy: `packages/deploy/flows-dev.mjs` mapeia cada `provision-flow-*.ps1` aos arquivos que o afetam e `push-flows-dev.ps1` roda os pendentes (os que mudaram desde a tag `flows-dev-publicado`, tag ausente = nada pendente) na conta de serviço (`az login` do service principal), depois de gerar as constantes dos flows de IA quando preciso. Só atualiza flow que já existe no DEV (estado ligado/desligado e URL do gatilho preservados); os argumentos obrigatórios vêm das variáveis `FLOW_*` do environment `dev`. Se um flow falha, os outros seguem, a distribuição roda, o Deploy termina vermelho com as causas no resumo e a tag não anda; `workflow_dispatch` aceita `forcar_flows` (nomes ou `todos`; execução forçada não move a tag). **Flow novo, schema (`provision-*` sem flow) e `sitemap:*` continuam à mão**: o flow novo nasce com dono na conta de serviço e não liga (`ConnectionAuthorizationFailed`), e o resto usa `az login` e conexões do usuário; rodam só do checkout principal na `develop` atualizada, nunca de feature, worktree ou sessão cloud, e nunca dois em paralelo nem junto com o Deploy.
- **Distribuição.** No fim do Deploy e de todo `pnpm push` local, `packages/deploy/solucoes/distribuir-apos-push.ps1` distribui nas 4 soluções (`BetinhosCore`, `BetinhosAutomacao`, `BetinhosInterface`, `BetinhosMotoristas`) o que entrou na AppBetinhos do DEV e confere. Nunca derruba o push; se a conferência não zerar, mostra "ATENCAO" e o export fica barrado até corrigir (skill `verificar-solucoes`). Tipo de componente novo pede regra em `packages/deploy/solucoes/regras.json`.
- **PROD.** Push na `main` dispara o workflow "Produção" (`producao.yml`). `packages/deploy/caminho-publicacao.mjs` escolhe o caminho pelos arquivos mudados desde a tag `prod-publicado`:
  - só a tela (`apps/shell`, `packages/dataverse`, lock) → direto ao PROD (`push-front-prod.ps1`, environment `prod-front`, sem revisor; vira camada Active que o próximo import das soluções retira);
  - só código de plugin que já existe no PROD (`packages/plugins/Cr40f.<Nome>.Plugin/`) → copia para o PROD o assembly que o DEV já usa (`exportar-plugins-dev.ps1` com a trava do commit, depois `push-plugins-prod.ps1`, environment `prod-front`, sem TEST nem backup, decisão do Renan de 05/11/2026; vira camada Active que o próximo import das soluções retira). Tela e plugin juntos fazem os dois caminhos rápidos. Registrador, step e Custom API novos vão pelas soluções;
  - qualquer outra coisa (ou arquivo desconhecido) → "Publicar soluções" (`publicar.yml`, `test-e-prod`): trava do commit (a tela e os plugins do DEV têm de ser os da `main`), conferência e export do DEV, ensaio no TEST, backup e PROD com os mesmos pacotes e aprovação do Renan no environment `prod`; perda reprova (skill `verificar-solucoes`). Solução com o mesmo conteúdo da última publicação que passou no ambiente é pulada (tag `solucoes-<alvo>`: versão e hash de cada uma; `importar_tudo` força);
  - só documentação/CI/skills → nada; a tag anda.
  A tag só anda quando a publicação passa.
- "Publicar soluções" à mão continua valendo (`test`, `test-e-prod` ou `prod`) para refazer um ensaio. "Retirar AppBetinhos" (`retirar-caixa.yml`) é a segunda janela da promoção. Para zerar o TEST, `pac admin copy` do PROD (como no ensaio de 22/10/2026).
- Nada que mude o PROD fica fora do repositório: valor que difere por ambiente vai em variável de ambiente ou connection reference, nunca fixo no flow. Nunca publicar no PROD por outro caminho.

## Ambiente cloud (sessões cloud do Claude Code)

- Ambiente em claude.ai/code: variável `NODE_AUTH_TOKEN` (token GitHub com `read:packages`), sem credenciais do Dataverse. O preparo da VM roda no hook SessionStart (`.claude/hooks/session-start.sh` → `scripts/cloud-setup.sh`, log em `/tmp/cloud-setup.log`), porque o token não chega ao setup script do ambiente; o setup script pode ficar vazio.
- Na VM o app roda em modo mock (`isLocalHost()`): sem dados do Dataverse, só navegação e UI. Dá para codar, rodar `pnpm typecheck`, `pnpm test`, `pnpm dev` (porta 36472) e verificar a UI no Chromium headless.
- Comportamento que depende de dados reais, Custom API, plugin ou Flow não é verificável na VM: a sessão cloud entrega o PR e declara essa parte como "não verificada na nuvem"; a verificação com Dataverse DEV é feita localmente.
- Sessões cloud nunca executam `pnpm push`, `pnpm wr` de publicação, `sitemap:*`, `push:plugin:*` nem scripts de `packages/deploy/provision-*` (todos alteram o Dataverse e exigem a `develop` no checkout principal).
- Skills de verificação ficam em `.claude/skills/` (versionadas) para valerem também nas VMs.
